# MelilloDesign document workflow

This specification records the requested product behavior and the evidence needed to accept it. The immediate goal is to make a new document project understandable from its first screen through context confirmation and the first editable Blockout. The engineer supplies and decides the technical content; MelilloDesign supports its graphic presentation.

The work is complete when a new project can follow this flow in Chrome with the real Codex CLI, the checks below pass, and the result is recorded here. Stop after that validation; producing a finished tender or report is outside this implementation task.

## Header/footer extension · 24 October 2026

The requested [header/footer workflow](melillodesign-header-footer.md) adds a
stage before page Blockout for documents using these recurring regions:
collect logos and guidance, choose or create a reusable project design, edit
its structure, finish and approve its actual graphics, then apply its measured
reservations to the page plan. Fast technical documents must ask the same
editorial questions in chat. The project library and lifetime editor include
an explicit per-document follow-updates option covering changes from any
linked document or its agent. That extension has its own acceptance matrix
and is not covered by the historical delivery records below.

## Required sequence

Open the app → choose **Create new project** or **Open existing project**. The wizard contains **only document type (with preset deliverables) and working/additional folders**. It then opens chat. Main-text reading starts automatically, with an explicit chat explanation and honest coverage. In chat, show image preparation selected by default, with an opt-out checkbox and one **Continue and prepare documents** action; then start the real Codex preparation conversation automatically. Codex explains the relevant documents and groups related choices into a short native form in chat. The engineer corrects purpose and graphic constraints through ordinary replies or the existing question-form flow, then confirms the short resolved brief and chooses manual Blockout or agent proposals. Compare and edit pages, then explicitly approve a structure before graphic design. Blockout remains editable during graphic design. Existing projects resume their saved stage.

The user explicitly moved every preparation choice out of the wizard on 2026-10-23: image intake, material readiness, brief/context review, constraints and Blockout approach all belong in chat. There is no Images or Context wizard step, no setup-review modal, and no fixed app-owned readiness/purpose/constraint questionnaire inside chat. Merely moving the former wizard questionnaire into the transcript does not satisfy the conversational requirement. Negative image consent is saved distinctly from an unanswered question. Following the later 2026-10-23 correction, image preparation is selected by default in chat; clicking Continue explicitly saves that choice and starts processing. Merely opening the project does not start image processing. Ordinary preparation conversation is allowed before confirmation, while Blockout/design generation remains gated.

Quick context inspection and image intake are different operations. Reading relevant searchable text prepares the brief. Extracting, cropping and tagging images is the optional background job. Neither job may be presented as completed before it actually completes.

The later 2026-10-23 correction replaces the earlier one-question-per-turn policy: correlated choices belong together in an agent-generated native chat form with `layout: "grouped"`. The engineer reviews and edits the whole group before submitting once. This does not restore a fixed setup questionnaire or move choices back into the wizard. Final brief approval remains explicit.

## Persistence and surfaces

The setup records category/subtype, purpose, working destination, additional authorized context roots, intake consent, source-backed suggestions, user corrections, confirmation and the chosen Blockout approach. Reloading must resume the current setup stage rather than invent a new project or restart intake.

The daemon HTTP API owns the setup. UI and `od` CLI use the same endpoints and shared TypeScript DTOs. CLI input supports `--prompt-file <path|->` and machine-readable output supports `--json`. Agent context receives the confirmed brief privately; chat and the file browser must not expose internal JSON as the user's document.
